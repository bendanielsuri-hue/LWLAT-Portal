# MAT Panel Meetings reuse Panel/PanelGroup instead of a new model

MAT Panel Meetings — a MAT-wide meeting that discusses only Escalated referrals, usually launched urgently for one student at a time from the Escalations screen — are not a new model. A MAT Panel Meeting is a `Panel` belonging to a MAT-wide `PanelGroup` (`school=null`), distinguished from a school Panel purely by which group it's in. It inherits `Panel`'s existing status machine, agenda (`PanelReferral`), discussion, notes, and actions-raised mechanics unchanged.

Two constraints make this reuse behave correctly for the MAT case without new UI:

- **Eligibility is Escalation-only.** `inclusion_panel_meeting_setup`'s "unassigned referrals" list already branches per `Panel`; for the MAT group it's replaced with "referrals carrying an open `Escalation`, not already on this panel's active agenda," MAT-wide rather than school-scoped. There is no path to add a non-escalated referral to a MAT agenda — if one needs MAT-level attention, it must be escalated first. This depends on Escalation being a clean, unambiguous signal: at most one *open* Escalation per referral at a time (history preserved across escalate → resolve → re-escalate cycles), so "does this referral belong on a MAT agenda" is always a yes/no fact, never "which of several open escalations."
- **Only one MAT Panel Meeting may be `running` at a time**, enforced everywhere (Quick Launch appends to the already-running one instead of creating a second; Start Meeting is disabled on any other MAT panel while one is live). School Panels have no equivalent limit — this is MAT-group-specific.

Quick Launch (the primary way MAT meetings get created) checks for an already-running MAT panel: none running → create one directly in `running` status (skipping `draft`/`ready`) with the triggering referral's `PanelReferral` pre-added and discussion already started; one running → append the referral to its agenda instead. Appending mid-meeting reuses the Agenda page's existing "Add to Agenda" link into Setup's `add_referral` action — already generic and append-only against a running panel — rather than adding a new composition capability. A running MAT panel's Agenda page shows a page-load count of open Escalations not yet on its agenda to prompt the chair toward that same link.

## Considered options

- **A dedicated `MatPanelMeeting` model, separate from `Panel`**: rejected — would duplicate the entire status machine (draft/ready/running/delayed/complete/void), agenda linking, discussion timing, notes, and actions-raised mechanics for no behavioural difference beyond "which referrals are eligible" and "how it gets created." `PanelGroup.school` was already nullable, so a MAT-wide group fits the existing shape with zero schema changes.
- **A new "Agenda edit while running" UI, built specifically for MAT meetings**: rejected once we found the Agenda page already links to Setup's `add_referral` action with no `running`-status guard blocking it — building a parallel mechanism would have meant maintaining two ways to add a referral to a live agenda for no reason.
- **No single-running-panel limit; let Quick Launch always spin up a new `Panel`**: rejected — without the limit, two chairs could each be running "the MAT panel" simultaneously with no way to tell which is canonical, and Quick Launch's "append to the running one" behaviour would have nowhere reliable to append to.
- **Let Escalation stay unbounded (multiple simultaneous open rows per referral)**: rejected — MAT eligibility would become "does this referral have at least one open Escalation" instead of a clean binary fact, and the Escalated status pill would need to either pick one arbitrarily or show a count, both worse than the current single-open-row invariant with full history preserved underneath it.
