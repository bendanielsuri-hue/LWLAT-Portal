{% comment %} One entry in an Action's Updates thread. Its own fragment because the same markup is rendered twice: server-side for the thread the modal opens on, and again on its own as the JSON answer to a post, which the Updates step appends in place (see inclusion_panel_action_new and dialogs/action-form.js). Two copies of this markup would drift the moment either side changed. Every entry carries its own author header, where the Discussion's thread collapses consecutive entries by the same author under one ({% ifchanged %}). That comparison needs the previous entry in the same loop, and an entry posted here is rendered on its own with nothing to compare against - so the grouped form would be wrong exactly half the time it rendered. Reuses the portal-wide .note-thread component the Discussion's own note thread uses - a dated, attributed entry is the same thing on both pages, and nothing here is action-specific. Edit/delete is author-only. `update.can_edit` is computed server-side (view compares update.author_id against the current-staff cookie identity) rather than here, since the same check has to happen again when the button is actually clicked - this only decides whether to offer it. The buttons and the inline edit form themselves live in the shared `_thread_entry_edit_delete.html` partial, not here, so the meeting-note thread can reuse the identical UI once it moves onto the same core.ThreadEntry base (#236). {% endcomment %}
